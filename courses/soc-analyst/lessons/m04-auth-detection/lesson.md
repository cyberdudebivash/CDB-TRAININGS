# SOC-M04 - Authentication-attack detection and triage

## Learning objectives

By the end of this module you can:

| ID | You can... |
|---|---|
| **LO1** | Distinguish password guessing, password spraying and credential stuffing from event patterns and explain which evidence supports each. |
| **LO2** | Interpret Windows 4624/4625 fields (logon type, status and sub-status, source address) to say how a logon was attempted and why it failed. |
| **LO3** | Implement Sigma correlation rules for single-account guessing, single-source spraying and distributed spraying, and measure their precision and recall on labelled telemetry. |
| **LO4** | Triage an alert into a documented decision with evidence, including checking for a success after failures. |
| **LO5** | Tune a noisy detection with a narrow, owned, expiring suppression and show that no attack scenario was lost. |
| **LO6** | Map the activity and your actions to ATT&CK T1110 sub-techniques and CSF 2.0 Functions, citing the framework versions. |

Every objective is taught here, practised in a lab, and assessed (see `curriculum/outcomes.yaml`).

## 1. Why this matters

Guessing passwords is cheap, so authentication failures are among the noisiest data a SOC sees - and one of the few places where
a quiet, patient attacker and a broken backup job look almost the same. Two mistakes are common:

1. **Rules that only count failures per account** never see an attacker who tries one or two passwords on *hundreds* of accounts.
2. **"Tuning" that deletes noise without measuring** silently removes the one night the noise was an attack.

In this module you build detections *and* the habit of proving them: every rule is run against labelled synthetic telemetry that
contains attacks, benign look-alikes and a plain-looking compromise, and you read precision and recall off the result.

> **Safety and ethics.** All data in this module is generated by code; nothing is real. Never test credential-guessing against any
> system you do not own or have **written authorisation** to test. The labs never touch a network.

## 2. Read the evidence (LO2)

Windows records a failed logon as **Security event 4625** and a successful one as **4624**. The 4625 is written on the computer
where the attempt was made - a workstation, a member server (e.g. an RDP host) or a domain controller - so the *same* attack can
leave evidence on several machines.

| Field (as exported) | What it tells you |
|---|---|
| `TargetUserName`, `TargetDomainName` | The account the attacker *tried* (it may not exist). |
| `IpAddress` (shown as "Source Network Address") | Where the attempt came from. Behind a NAT or VPN gateway many people share one address. |
| `WorkstationName` | Machine name supplied by the client; easily forged. |
| `LogonType` | How the logon was attempted (table below). |
| `Status`, `SubStatus` | Why it failed (table below). |
| `AuthenticationPackageName` | NTLM, Kerberos or Negotiate. |

**Logon types you will meet most** (Microsoft documentation): `2` Interactive (at the keyboard), `3` Network (e.g. file shares,
many remote protocols), `4` Batch, `5` Service, `7` Unlock, `10` RemoteInteractive (Remote Desktop / Terminal Services).
Types 8, 9 and 11 also exist.

**Failure codes used in this module** (all documented by Microsoft):

| Code | Meaning (documented) | Analyst reading |
|---|---|---|
| `0xC000006D` (Status) | Bad user name or authentication information | The generic "it failed"; read the SubStatus. |
| `0xC000006A` (SubStatus) | Bad password | The account exists. |
| `0xC0000064` (SubStatus) | Misspelled or bad user account | The account does not exist; *several in a row* can indicate user-name enumeration. |
| `0xC0000234` | Account locked out | A lock-out already happened. |
| `0xC0000072` | Account disabled by an administrator | Probing a disabled account. |

> An attacker's *failures* are only half the story. The **4624 success** that follows decides whether this is an attempt or a compromise.

## 3. Three patterns, one family (LO1)

ATT&CK groups online password attacks as **T1110 Brute Force** (Credential Access) with sub-techniques *T1110.001 Password Guessing*,
*T1110.002 Password Cracking*, *T1110.003 Password Spraying* and *T1110.004 Credential Stuffing*. For authentication logs the
useful question is: **what varies - the account, the source, or the password?**

| Pattern | Typical shape in 4625 data | Group by | Count |
|---|---|---|---|
| Guessing (T1110.001) | One account, many attempts, one or few sources | account + source | events |
| Spraying (T1110.003) | Many accounts, one or two attempts each, one source | **source** | **distinct accounts** |
| Distributed / low-and-slow spraying | Many accounts, sources rotate, rates stay low | network, or **account** | distinct accounts, or distinct sources |
| Credential stuffing (T1110.004) | Mostly *valid* user names from another breach, about one attempt each, many sources | account / source | distinct accounts; compare with success rate |

Password cracking (T1110.002) happens offline on stolen hashes and leaves no 4625 trail, so it is out of scope here. Credential
stuffing reuses real credentials from other breaches; compared with spraying it tends to show valid user names and a higher share of successes,
which is why success events and user-directory context matter (this is the course's own explanation, not ATT&CK's wording).

```text
        group by ACCOUNT                 group by SOURCE                    group by NETWORK (/24)
   +-----------+                      +-----------+                      +-------------------+
   | j.doe     | <- many events       | 203.0.113.7| -> many accounts    | 192.0.2.0/24      | -> many accounts
   +-----------+   from 1 source      +-----------+   1-2 events each    |  .10 .11 .12 ...  |   from several sources
   catches GUESSING                    catches SPRAYING                    catches DISTRIBUTED spraying
```

## 4. Detections that work - and one that does not (LO3)

### The baseline: the playbook rule

The *SOC Analyst Survival Playbook* (p. 22) describes a "classic" rule: **more than 5 failures in 300 s, grouped by source IP, target user
and target host**. Written as a Sigma correlation (`labs/m04-guided/rules/naive_playbook/`) it looks right and does catch guessing.
But it groups by *target user*: a sprayer tries one or two passwords per account, so no group ever reaches six. You will **measure**
this in the lab: on the guided dataset the rule detects **1 of 5** attack scenarios and still raises a false positive.

### Sigma correlation in 30 seconds

A Sigma *detection rule* says what one event looks like. A Sigma *correlation rule* (Sigma specification 2.1.0) counts matches of
other rules over time:

```yaml
title: Failed Windows Logon
name: win_failed_logon
id: 7f3c8a52-5d1e-4b7a-9c64-0a1b2c3d4e01
logsource: {product: windows, service: security}
detection:
  selection:
    EventID: 4625
  condition: selection
---
title: Password Spraying From One Source
name: mr_spray_single_source
id: 2b3c4d5e-6f7a-4b8c-9d0e-1f2a3b4c5d11
correlation:
  type: value_count        # count DISTINCT values of a field
  rules: [win_failed_logon]
  group-by: [IpAddress]    # one counter per source address
  timespan: 10m
  condition:
    field: TargetUserName  # ...of this field
    gte: 10                # ...at least 10 distinct accounts
```

- `event_count` counts matching events; `value_count` counts **distinct values** of `condition.field`.
- `group-by` is the *scope of the counter*. Choosing it is the whole design decision (section 3).
- `timespan` accepts `s`, `m`, `h`, `d`.

**The lab evaluator** (`soc_lab`) implements a documented subset of the specification and **fails closed**: an unsupported feature is an
error, never silently ignored. It is a *teaching* tool, not a SIEM. Its choices: the window for an event is the last `timespan` up to
that event; an alert fires the first time the condition holds and is *extended* while it keeps holding; it re-arms when the condition
stops holding. A real SIEM may count differently - always test your rules on your platform.

### Choosing thresholds from data, not from folklore

A threshold is a hypothesis about "normal". In the guided dataset a morning VPN rush produces **14** distinct mistyping users from *one* address
(everyone shares the VPN NAT) while the real sprays reach **27 to 48** distinct accounts in ten minutes. A single global threshold of 10 raises a false positive; a global
threshold of 20 would still be a guess that an attacker who sprays 18 accounts walks under. The better design is **role-aware**: the VPN gateway (known from the asset inventory) gets a higher
threshold *and its own rule*, while everything else keeps 10.

## 5. Triage (LO4)

Triage turns an alert into a *decision someone else can audit*. Use this order:

1. **What fired?** Read the group (source, account, network) and the metric (events or distinct accounts).
2. **What is the shape?** Fixed interval and one account (a retry loop), many accounts at human speed (a mass typo), many accounts at
   machine speed (a spray), one account at machine speed (guessing).
3. **Who is the source?** Asset inventory: scanner, VPN gateway, backup server, external?
4. **Is there a reason?** Change calendar: is there an approved activity for this source *at this time*?
5. **Did it work?** Search for a **4624 success** from the same source for any account in the alert.
6. **Decide and record:** classification, severity, confidence, evidence (event IDs), disposition, next steps.

| You find... | Classification | Disposition |
|---|---|---|
| Failures only, external, machine speed | True positive - attack | Block source; watch the account |
| Failures **then a success** from the same source | True positive - **compromise** | Escalate to incident response; reset the account |
| Trusted source, **no** approved change at that time | True positive or suspicious | Escalate: the trusted source may be compromised |
| Trusted source inside an approved change window | False positive - benign activity | Close with a *time-bounded* suppression |
| One service account, fixed interval, expected host | False positive - misconfiguration | Close with a narrow suppression **and fix the credential** |

The checker in the labs verifies the objective parts of your record (cited events exist and relate to the alert, required context was consulted,
the decision is defensible, a suppression is narrow). A human reviewer grades the quality of your reasoning with the rubric.

## 6. Tune without blinding yourself (LO5)

A suppression is a promise: "I understand this noise and accept the risk of hiding it". Make that promise **narrow, owned, justified and expiring**:

| Rule | Good | Bad |
|---|---|---|
| Match | `TargetUserName: svc-backup` **and** `IpAddress: 10.0.2.15` | `LogonType: 3`; `10.0.0.0/8`; wildcards |
| Time | `10:00-10:30` for an approved scan | none, or "until further notice" |
| Ownership | `ticket: CHG-1042`, `owner: secops` | no ticket |
| Fix | rotate the stale credential, then delete the exception | leave the exception for ever |

After **every** tuning change re-run the detection and read two numbers: *recall on attack scenarios* (unchanged?) and *suppressed alerts that were real attacks* (must be zero). In the dataset the scanner address `10.0.5.20` appears twice: legitimately at 10:02 and
**again at 14:10 without a change ticket** - a time-bounded suppression still catches the second, a permanent one does not.

```yaml
exceptions:
  - id: EX-F2-scanner-change-window
    rule: mr_spray_single_source
    match: {IpAddress: 10.0.5.20}
    reason: "Authorised scan approved in change CHG-1042 for 10:00-10:30 UTC only."
    ticket: CHG-1042
    owner: secops
    valid_from: "2026-03-02T10:00:00Z"
    valid_until: "2026-03-02T10:30:00Z"
```

## 7. Frameworks and response context (LO6)

- **ATT&CK** (*Enterprise v20, T1110 page v2.8*): tag detections with `attack.t1110.001` or `attack.t1110.003`. ATT&CK is a knowledge base
  of observed behaviour, not a coverage checklist.
- **NIST CSF 2.0 Functions** used in this module: *Detect* - continuous monitoring (**DE.CM**) and adverse-event analysis (**DE.AE**);
  *Respond* - incident management (**RS.MA**), analysis (**RS.AN**) and mitigation (**RS.MI**); *Protect* - identity management,
  authentication and access control (**PR.AA**), where MFA and lock-out policy live.
- **NIST SP 800-61 Rev. 3** (April 2025) organises incident response around the CSF 2.0 Functions. It does **not** define a numbered phase list;
  the older four-phase model belongs to Rev. 2, and the six-step Preparation-Identification-Containment-Eradication-Recovery-Lessons model is a
  common practitioner convention, not a NIST definition.
- **Legal reporting.** Some jurisdictions impose reporting deadlines for listed incident types (for example, India's CERT-In Directions of 28 April 2022
  require reporting incident types listed in their Annexure I within 6 hours of noticing). Involve legal and compliance; this course does not give legal advice.

## 10. Common mistakes

- **Grouping by the wrong key.** Count the thing that varies: accounts for sprays, events for guessing.
- **Raising the global threshold** to silence one noisy source and thereby blinding yourself to a 15-account spray.
- **Trusting an address forever.** A scanner, a jump box or a VPN gateway is only trusted *for its purpose and time*.
- **Stopping at the failures.** No 4624 search, no triage.
- **Suppressing instead of fixing.** The stale service-account password is still wrong tomorrow.
- **Counting NAT as a person.** One VPN address can legitimately stand for dozens of users.
- **Forgetting lock-out interplay.** Aggressive lock-out policies turn a spray into a denial-of-service on your own users.

## 11. Troubleshooting the labs

| Symptom | Likely cause | Fix |
|---|---|---|
| `RULE ERROR: ... unsupported modifier` | A Sigma feature outside the supported subset | Use the supported modifiers listed in the lab README |
| `RULE ERROR: group-by must be a non-empty list` | Correlation without `group-by` | Add the key that scopes the counter |
| Zero alerts | Rule runs on `events.jsonl` but uses `SrcRole`/`SrcNet24` | Run `soc_lab enrich` and use `events.enriched.jsonl` |
| Everything alerts | Condition uses `lt`/`lte` (true for one event) | Use `gte`/`gt` for detections |
| `exceptions invalid ...` | Missing owner/ticket/expiry, wildcard, or validity over 90 days | Fix the field named in the message |
| Times look wrong | Mixed time zones | All data is UTC (`Z`) |

## 12. Security and operational considerations

- **Data handling:** real authentication logs contain user names and source addresses (personal data). Collect and retain only what the use case needs.
- **Alert fatigue is a security risk:** a rule that fires 25 times for one campaign (one alert per sprayed account) buys coverage at the price of attention; discuss roll-ups.
- **Detection drift:** thresholds go stale as the business changes; schedule reviews and keep the regression data.
- **Independence of evidence:** attackers can forge `WorkstationName`; prefer fields the attacker cannot control cheaply.
