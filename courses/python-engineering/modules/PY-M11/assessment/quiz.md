# PY-M11 knowledge check (8 questions)

Formative: it checks understanding of the lesson and is **not** evidence of competence on its own (the independent lab is). The answer key is held by instructors and is not published.
Questions are generated from `quiz.yaml`; each is tied to a learning outcome.

| # | Outcome | Question | Options |
|---|---|---|---|
| Q1 | LO1 | The handbook's log monitor counts matches per keyword and sends an alert whenever the count is at least 5. For 100 identical ERROR lines it sends 96 alerts. What does the code implement, and what should the specification say instead? | A) It alerts once for each keyword; the specification should add the count to the alert text so that an operator can see at a glance how many lines matched in total. B) It alerts on every line from the fifth on; the specification should say one alert when the threshold is crossed and a new one only after the count has dropped below it. C) It alerts on every fifth line; the specification should say every tenth line, so that fewer alerts are sent for the same number of error lines in a day. D) It is correct, because an operator wants one alert for each error line; the specification should say that the threshold decides only when the alerting begins. |
| Q2 | LO2 | A wheel built from your project is named `app-1.0.1-py3-none-any.whl`, but the installed command prints `app 1.0.0`. What went wrong, and what is the lasting repair? | A) The wheel was built from a stale copy of the code; delete the `build` folder before every release and rebuild until the two numbers agree again. B) pip rewrote the version while installing the wheel; pin pip to the version that was used for the release so that it stops doing that in future. C) The version is written in `pyproject.toml` and in the code and only one was updated; compare the two by hand in the release checklist before anybody tags a release. D) The version is stated in two places; keep one source (the package's `__version__`, read by the build) and let a check compare the wheel with the program. |
| Q3 | LO3 | Your tests reach 100 percent branch coverage. A colleague changes `now >= exp` to `now > exp` in the expiry check and every test still passes. What is the most useful addition, and what does it say about coverage? | A) A test at the boundary (`now == exp` must count as expired); coverage shows that code ran, not that a change in what it does would be noticed. B) More tests with random values of `now`; coverage was counted wrongly, because a branch that no test enters must still exist in the expiry check. C) A rule that coverage must stay at 100 percent for statements and branches; the colleague's change was not covered and the rule would have caught it. D) Nothing; the two forms differ only at one instant that does not matter in production, so the tests are right to treat them as the same. |
| Q4 | LO3 | A fast sliding-window counter and a slow version that follows the specification line by line disagree on one of 2000 random inputs. What does that prove, and what do you do? | A) The slow version is wrong, because the fast one passed every hand-made test; delete the slow version, which only exists to be compared. B) The generator is unfair, because real data never has equal timestamps; make the generator avoid them and run the comparison again. C) At least one of them is wrong for that input; shrink the input, decide from the specification which is right, fix it and keep the case as a test. D) Nothing, because random tests cannot be reproduced; drop the comparison and rely on the hand-made examples that already pass in the pipeline. |
| Q5 | LO4 | The gate parses a workflow file with PyYAML and finds `python-version: [3.10, 3.11, 3.12]`. What does the parser hand over for the first entry, and what is the repair? | A) The text `3.10`, as written; no repair is needed, because a YAML list of versions is always read as a list of strings by the parser. B) The text `3.10`, but in an order chosen by the parser; add a sort key to the matrix so that the versions run from the oldest to the newest. C) The number 3.1, so that the repair is to write the entry as `3.100`; the extra digits keep the number from being shortened by the parser. D) The number 3.1 (a float), which is not the text `3.10`; write every version as a quoted string such as `"3.10"`, which is a string in every parser. |
| Q6 | LO4 | A workflow step runs `echo "${{ github.event.pull_request.title }}"`. Why is that a problem, and what is the documented mitigation? | A) The expression is evaluated by the shell on the runner, so the title may not contain quotes; reject every pull request whose title has quotes in it. B) The text is pasted into the script before it runs, so a title can add commands; set the expression to an environment variable and use the variable in the script. C) The title is secret information that the runner prints to the log; move the step to a job that only the maintainers of the repository are allowed to start. D) The step is slow, because the title must be fetched from the API at run time; cache the title in an artifact and read it from there instead of calling the API. |
| Q7 | LO5 | `authwatch scan big.jsonl \| head -1` ends with a traceback. Which exception is it, and how should the tool end instead? | A) `BrokenPipeError`: the reader left, so the next write fails; stop writing, point the output at the null device so that no later write can fail, and leave without a message. B) `KeyboardInterrupt`: the shell sent Ctrl-C when the reader left; catch it and exit with status 130 so that the shell can tell what happened. C) `MemoryError`: the reader left with the buffer still full; write the report in smaller pieces so that the buffer never fills up completely. D) `UnicodeEncodeError`: the reader cannot decode the output; write the report with `errors="ignore"` so that every byte is accepted by the reader. |
| Q8 | LO6 | The pipeline of a project runs `ruff` and `pytest` as two separate steps, while developers run `python scripts/check.py`, which also runs mypy and builds the wheel. What is wrong, and what is the repair? | A) Nothing is wrong; the pipeline should be fast, so it is right to run fewer checks than a developer does, who has more time before a release. B) The developers' command is too slow; remove mypy and the build from it so that the laptop and the pipeline run the same two checks again, as before. C) The pipeline is not running the checks that decide whether a change may merge; make the pipeline run `python scripts/check.py`, the one command that defines done. D) The pipeline is correct but its steps are in the wrong order; run `pytest` before `ruff` so that a failing test is reported before any style problem is. |

**Scoring:** instructors apply the key; 6/8 is the formative checkpoint.
